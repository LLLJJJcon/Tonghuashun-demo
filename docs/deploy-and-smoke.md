## 4. 发现的问题（按严重程度排序）

> 按要求没有修改 `src/`、`public/data/`、`data/` 中的任何内容。下面的问题交给对应 agent 或主 agent 处理。

### P1：影响验收结论

**P1-1　真实数据中无法演示「人工修正」版本（D6）**
- 现象：12 条真实复核条目，无论确认、改性质（改为 4 种性质中的任意一种）还是标为噪声，在任何检查点、单条或任意两条组合（共 8,377 种）都不会改变事件快照，所以不会出现「人工修正」版本。复核提交后只更新队列和主张权重。原因：A 案例在 09-19 能把状态推到部分证实的 A03_c1（推测，D 级）置信度不低，没有进入复核队列；进入队列的 A03_c2 立场是「无关」。其余复核条目出现时，结论已经被 S 级事实锁定。
- 复现：到最新 → evt_B → doc_B03「确认归属」并填写理由后提交 → 版本历史仍是 v1–v3。也可以运行本轮使用的遍历脚本（思路：对每个检查点的 `review_queue` 逐条注入 ReviewEntry 后调用 `derive()`，检查是否出现 `is_human_correction`）。
- 涉及：`public/data/claims.json`、`public/data/documents.json`（AI 结果本身），`src/engine/review.ts`（复核队列规则），`agent-docs` B.7、B.8。
- 引擎和前端是正常的：用开发样例能生成「人工修正」版本（截图 19）。
- 建议（由主 agent 和人决定，不得编造 AI 错误）：① 接受现状，在测试说明和视频中说明「真实数据中的复核不改变结论，人工修正版本的链路用开发样例验证」；② 或者在 A 案例的复核候选中找一个确实存在歧义、处理后会改变状态的对象。例如 A03 的同一事件判定或转载判断，前提是 AI 实际给出的置信度确实低于阈值。不能为了演示改写 AI 输出。

**P1-2　没有「未解决冲突」（验收清单「证据冲突」）**
- 现象：29 个检查点中只有 `evt_A_stance` 一个冲突，出现时就已解决。验收清单要求「至少 1 个已解决冲突和 1 个未解决冲突」，不满足。首页卡片和事件页都没有出现过「未解决冲突」标签。
- 复现：任一时刻打开 evt_A、evt_B 的「证据冲突」区，或者遍历 `derive()` 输出中的 `conflicts`。
- 涉及：`public/data/claims.json`。`cases.md` 原本预期 B05「约 1 亿元」与 B04 构成要素冲突，但 B05_c1 实际抽取的值是 10,038.70 万元，所以没有形成冲突。另外，A02/A03 的推测在 A04 之前没有反对方。
- 建议：由主 agent 和人决定是否接受，并在 README「已知边界」中写明；或者确认真实材料中是否有官方事实到达之前的真实对立说法。

**P1-3　页脚声称「并经人工校验」，与实际不符（合规 / 硬约定 4「不编造」）**
- 现象：页脚写着「运行时不调用 AI：AI 结果在数据准备阶段基于真实材料生成，并经人工校验。」，而本轮所有 `prep_check.status = unreviewed`，主张详情显示「未经人工校验」，同一页面内前后矛盾。
- 涉及：`src/ui/components/Chrome.tsx` 第 35 行（AGENT-3）。README 第 12、88、89、267 行也有「经过人工校验」的表述（AGENT-5）。
- 建议：改为如实表述，例如「……生成，并经独立 AI 交叉复核，尚未人工校验」，具体以主 agent 和人确认的口径为准。

### P2：影响演示观感或理解

**P2-1　「到最新」跳到 2027-06-30 23:59，权重全部衰减到下限**
- 现象：最后一个检查点来自 doc_C05_c2（立场「无关」的观点「截至 2027 年上半年建设 10–12 条生产线」）的 `valid_until = 2027-06-30`。因此「到最新」把演示时钟设为 2027-06-30 23:59，比最后一条材料（2026-10-08）晚约 9 个月，也晚于今天。在这个时刻，几乎所有主张的时效衰减都到了下限 0.2：例如 A04（S 级事实）权重只有 0.200，evt_A 的支持 / 反对权重显示为 0.29 / 0.92，而在 2026-09-21 19:13 是 1.38 / 4.53。在最新时刻提交的复核，`demo_time` 也会记为 2027-06-30。
- 复现：点「到最新」，看顶栏时钟和任一主张的权重。
- 涉及：`public/data/claims.json` 中 doc_C05_c2 的 `valid_until`（AGENT-1），`src/engine/clock.ts` 的 `computeCheckpoints`（AGENT-2，会把所有非空 `valid_until` 都作为检查点，符合附录 B 的规定）。
- 建议：AGENT-1 确认这条无关主张是否需要设置有效期；或者由规则层面决定立场为 neutral 的主张的 `valid_until` 不作为检查点。修改规格需要主 agent 确认。

### P3：小问题

- **P3-1　没有网站图标，产生 `favicon.ico` 404**：真实 Chrome 的控制台会出现 1 条 `Failed to load resource: 404 (favicon.ico)`，对 D1「没有控制台错误」有轻微影响。建议在 `index.html` 加 `<link rel="icon" href="data:,">`，或者放一个本地图标。这属于前端入口文件，本轮没有修改。
- **P3-2　「只走本事件」在 A、D 中会停在 2026-09-05 01:02**：这一时刻只有 doc_A12（无关，候选事件为 A、D）到达，事件页显示「在当前演示时刻，这个事件还没有可见的材料」。涉及 `src/engine/clock.ts` 的 `eventCheckpoints`（候选材料也算本事件的时刻）。不影响结论。
- **P3-3　互动易两条材料的原文链接只到公司主页**：doc_C02、doc_C03 的 `url` 是 `irm.cninfo.com.cn/ircs/company/companyDetail?stockcode=301468…`，打开后要自己找到对应问答。涉及 `public/data/documents.json`（AGENT-1）。
- **P3-4　「信息时差」按发生时间区间的起点计算**：doc_A02 的发生时间是「2026-01-01 至 2026-09-18」（原文为「今年稍早」），页面显示「信息时差 261 天」，容易让人误解。涉及 `src/ui/pages/Timeline.tsx`。
- **P3-5　同一反应日的行情在 A02、A03、A04 三个节点上重复出现**：三者的反应日都是 2026-09-21（周五盘后和周末披露），所以显示相同的 +3.06%。这是 B.9 规则的正常结果，页面已经注明「不代表因果」，但同一个涨幅同时出现在传闻节点和否认节点下，可能引起误读。可以在 README「已知边界」中说明。
- **P3-6　材料级传闻横幅的范围偏大**：doc_A08 共 3 条主张，只有 1 条是传闻，其余 2 条是事实，但整条材料显示「传闻 · 未经证实：来源不明或匿名，无法核验」（`isRumor = claims.some(...)`）。财闻是署名媒体，这个文案不完全贴切。涉及 `src/ui/pages/Timeline.tsx`。
- **P3-7（环境说明）**：本机 5179 端口上已经有一个不是本轮启动的开发服务器（`DEV_SAMPLE=1`，PID 13754），本轮只借用它验证了开发样例中的人工修正，没有关闭它。
